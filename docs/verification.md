# Verification

## Independent reference model

The production engine represents positions as immutable tuples and uses negamax. `tests/oracle.py` uses separate integer bitboards, hard-coded win masks and X-max/O-min minimax. It does not import production board rules, winning lines or search helpers.

Starting from an empty board, the reference enumerator alternates players and stops at the first win or a full board. That generates 5,478 reachable positions, including 958 terminal positions. The test compares this set with the production validator's answers for all 19,683 possible raw encodings. Every legal transition is checked, not only the aggregate count.

## Search agreement

For every reachable state, the suite computes the reference value and the reference value of every legal candidate move. It compares those results against all four production strategies, including terminal states. This checks exact move scores as well as the chosen move, which catches incorrect bounds that happen to leave the final choice unchanged.

Separate symmetry checks exercise all eight transforms on every reachable board and establish the 765 canonical classes. A deterministic repeat check ensures caches do not leak between searches.

## The “cannot lose” claim

Starting from an empty board, the default perfect bot is fixed on one side while the other side is allowed **every** legal continuation. The traversal follows every human move sequence until termination and checks that the bot either wins or draws. It runs once with the bot as X and once as O.

This is an exhaustive property of this small game's reachable tree, not an empirical win rate. It assumes the bot controls its side from the start and the rules are followed. It does not mean that a solver handed an already losing arbitrary position can recover a draw.

## Interface boundaries

The core suite checks local rounds, scoring exactly once at termination, immutable failure on illegal moves, input validation, seeded random play, JSON output and perfect self-play. No display is needed.

`tools/gui_smoke.py` additionally creates real Tk widgets in a withdrawn window. It exercises hints, button invocation, score reset, terminal locking, both computer modes and cancellation of a pending callback when a new round begins. It requires Tk and a working graphical environment. This does not replace manual checks of font rendering, keyboard focus or platform appearance.

## Reproduction

```sh
python -m pip install .
python -m unittest discover -s tests -v
python tools/benchmark.py --check benchmarks/search.json
python -m tictactoe self-play --json
python tools/gui_smoke.py
```

The core suite currently contains 17 tests; several tests enumerate thousands of states internally. CI runs the core tests, all 16 benchmark comparisons, deterministic self-play and wheel creation on a six-job Linux/Windows and Python matrix. The Tk smoke is a separate display-dependent check.

## Visual evidence

The opening search chart is generated from `benchmarks/search.json` using a linear scale. The game diagram's hints come from the actual solver. The terminal image is generated by capturing actual CLI output, which is also committed as `docs/self-play.txt`. These illustrations are labelled and do not purport to be desktop screenshots.

To regenerate them:

```sh
python -m pip install -r requirements-docs.txt
python tools/render_docs.py
```

Image appearance can vary with available system fonts. No visual asset is needed to run the game.
